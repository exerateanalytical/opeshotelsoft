Architecture: Which foundation do we build on?

Three proven approaches — each maps to a different scale, team size, and deployment model

★ RECOMMENDED
Used by Shopify, Basecamp, Stack Overflow

A — Modular Monolith

One deployable application. Domain boundaries enforced in code, not in networks. Each module (Reservations, Housekeeping, Loyalty, POS, Finance) is a self-contained package talking through defined interfaces.

Pros

  • Single deployment — runs on one VPS/server
  • No network latency between modules
  • Easy transactions across modules
  • Fast to build, easy to debug
  • Works with smaller teams (5–20 devs)
  • Best fit for CEMAC infrastructure

Cons

  • Whole app deploys together
  • Must scale everything as a unit
  • Module boundaries require discipline
APALEO PATTERN
Used by Apaleo, Cloudbeds

B — API-First Platform Core

Lean core (identity, reservations, guest profiles, billing) exposed via REST/GraphQL. All other functionality built as first-party apps consuming those APIs. Same pattern the product will expose to partners.

Pros

  • Clean API from day one (partner-ready)
  • Apps can be deployed independently
  • Each app has own release cycle

Cons

  • More complex to build initially
  • Cross-cutting transactions harder
  • Requires solid API versioning discipline
ENTERPRISE SCALE
Used by Marriott, IHG, large Hilton systems

C — Microservices

Each domain (Reservations, Loyalty, Housekeeping, POS, Finance) is a completely separate service with its own database, deploy pipeline, and team. Services communicate via message queues + REST.

Pros

  • Scale each service independently
  • Team autonomy per domain
  • Technology freedom per service

Cons

  • Needs 50+ engineers to justify
  • Distributed transactions are hard
  • DevOps overhead is massive
  • Overkill for this stage
My recommendation: Option A (Modular Monolith). It is what Oracle OPERA and Mews started as — you get the full feature set of a hotel OS in a single deployable unit, with clean internal module boundaries ready to be extracted later if scale demands it. Perfect for CEMAC infrastructure where server reliability matters more than horizontal scaling.
