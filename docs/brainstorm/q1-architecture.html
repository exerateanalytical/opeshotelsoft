Question 1 of 5 — Architecture Foundation

This is the most consequential decision. Everything else is built on top of it.

★ RECOMMENDED Shopify · Stack Overflow · early Mews

A — Modular Monolith

One deployable application. Modules (Reservations, Loyalty, Housekeeping, POS, Finance) are self-contained code packages with clean internal interfaces — not separate services. Runs on one server.

SYSTEM DIAGRAM
📅 Reservations
🏨 Front Desk
⭐ Loyalty
🧹 Housekeeping
💰 Finance
🍽️ POS / F&B
⚙️ Shared Core — Auth · Events · Notifications · Config · Multi-tenant
🐘 PostgreSQL (single DB with schema-per-hotel)
⚡ Redis (cache + queues)

Why it wins

  • Deploys on one VPS — cheap, reliable, works in CEMAC
  • Cross-module transactions are trivial (same database)
  • Fast to build — no network calls between modules
  • 5–20 developers is the sweet spot
  • Easy to break into microservices later if needed

Trade-offs

  • Whole app deploys at once
  • Needs code discipline to keep modules clean
APALEO PATTERN Apaleo · Cloudbeds

B — API-First Platform

Lean core (identity, reservations, guest profiles) exposed via REST API. All other functionality — loyalty, housekeeping, POS — built as first-party apps consuming those APIs. Same API you'd expose to partners and third parties.

SYSTEM DIAGRAM
Staff App
Guest App
Loyalty
3rd Party
REST / GraphQL API Gateway
Core PMS Engine
Identity & Auth
PostgreSQL + Redis

Why consider it

  • Clean partner API from day one
  • Apps deploy independently
  • Partner ecosystem becomes possible earlier

Trade-offs

  • More complex to build initially
  • Cross-module transactions harder
  • API versioning discipline required from day 1
ENTERPRISE ONLY Marriott · IHG at massive scale

C — Microservices

Each domain is a completely separate service with its own database, deploy pipeline, and team. Services communicate via message queues. Justified only at 50+ engineers and millions of bookings per day.

Reservation Svc
Own PostgreSQL
Loyalty Svc
Own PostgreSQL
Finance Svc
Own PostgreSQL
Message Bus (RabbitMQ / Kafka)
API Gateway + Service Mesh + k8s

When it makes sense

  • 50+ engineers across teams
  • 1M+ bookings / day
  • Independent scaling per domain needed

Why not yet

  • Distributed transactions are genuinely hard
  • DevOps overhead is massive (k8s, service mesh)
  • Overkill for this stage — adds years to delivery
Recommendation: A — Modular Monolith. Oracle OPERA, Mews, and Cloudbeds all started this way. You get full HMS feature coverage deployed on a single server, with clean internal boundaries ready to split later. Perfect for CEMAC infrastructure.
